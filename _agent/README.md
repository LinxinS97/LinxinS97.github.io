# Profile page agent

Node 24+ for the local adapter. No npm dependencies are needed locally.

Build/start Jekyll on port 4000 (the rendered `_site/index.html` is required for the complete link directory), then from the repository root:

```powershell
node --env-file="$env:USERPROFILE/.config/linxin-page-agent/.env" _agent/local.mjs
```

The external env file contains `OPENROUTER_API_KEY`, `OPENROUTER_BASE_URL`, `VISITOR_HASH_SECRET` (a persistent random secret), and `ALLOWED_ORIGINS` (see `.env.example`). Secret values never go into frontend files, git, Jekyll config or generated HTML. On localhost the browser connects to the local proxy on port 4100. Published pages use the Cloudflare proxy configured by `page_agent_endpoint`. Secrets and visitor identifiers are never included in model prompts or error responses.

## Behavior

### Updating the profile

Edit `_includes/profile.md` for biography, contact details, research interests, publications, teaching, internships and service. This is the shared source for both the agent and the expandable page chapters; do not add secrets or private information. Keep `<!-- section -->` before each top-level chapter and retain the existing heading names so citation anchors stay stable. The homepage's compact identity header lives in `_pages/about.md`.

The local backend reads the Markdown file on every request. Jekyll renders it through `_includes/profile-details.html` with native `details` controls, so chapters work without JavaScript. Browser section tools read and search collapsed text silently: they do not open chapters, scroll the page or highlight evidence. Only a visitor clicking an answer citation opens, scrolls to and highlights the relevant section. Direct hash links also reveal their chapter. Chapter opening and closing use a cancellable 320 ms height animation, with instant transitions for reduced-motion preferences. Answers scroll only the chat transcript internally. Worker builds bundle the same Markdown using `node _agent/build-profile.mjs`; redeploy the Worker after changing it.

Uses `openai/gpt-6-luna` with `reasoning.effort: high` through OpenRouter tool calling, including paper reading. A separate model scope check rejects unrelated, mixed, or instruction-override requests before page actions. The agent then observes, optionally searches, silently reads evidence and answers with section citations. Browser tools operate on an allowlist of profile sections; they cannot evaluate code, use arbitrary selectors, open URLs, send messages, or modify the profile. This is DOM-based computer use in the current page, not OS-level control or screenshot-based remote desktop access.

Each new factual question first searches an index generated directly from the Markdown's sections, paragraphs and linked names. Token matches are ranked by how distinctive they are across the profile; Chinese bigrams are supported. Short references can use the previous question. Only after this lookup does the scope classifier receive the actual matched evidence plus the index's section/name directory. When translation, spelling or reference resolution caused a miss, it can supply up to three alternative search phrases for one retrieval retry before the final decision. There is no project/person exception list; editing the Markdown updates the index automatically. Retrieval is bounded to five excerpts of at most 1,400 characters. A keyword hit does not authorize an unrelated coding/tutorial request. Answers remain grounded in profile facts, and unsupported details about a known entity are acknowledged rather than treated as an unrelated topic. Answers and refusals follow the current question's language or explicitly requested output language, rather than previous conversation language. Refusals are localized within the existing classifier/tool call, with no extra translation request and no automatic bilingual suffix.

The `web_search` tool uses the existing OpenRouter key and its Exa web plugin only when a search is requested by the agent. It searches beyond the homepage links for in-scope subjects, with up to ten search attempts per question (including retries) and five results per search. Search incurs additional OpenRouter fees. Only public URLs from provider citation annotations become sources; unsupported URLs in generated text cannot become citations. Search failures produce no evidence. Results remain untrusted and cannot enable email tools. During a question, up to 32 source records share a 96 KB UTF-8 notes budget; this preserves earlier evidence while reading multiple batches. Across questions, only six cited documents are retained with the five-step memory bound. The browser displays progress without scrolling and opens source links only when clicked.

Answer citation IDs live only in structured fields and are rendered as source buttons/links. A shared server/browser sanitizer removes internal citation markers from new answers and saved visible conversations without removing ordinary bracketed prose.

Facts come from the owner-controlled `_includes/profile.md`, the actual contents of listed papers, and external pages linked from the site. `read_paper` accepts only IDs parsed from the profile's arXiv, ACL Anthology and PMLR publication links; it never accepts a user/model-supplied URL. It first retrieves arXiv HTML with a size/timeout/redirect bound, then falls back to the catalog's PDF via OpenRouter's `cloudflare-ai` file parser. Full text is converted into question-specific factual notes by the configured model, then used for the final answer. Up to three papers can be read together, at most 12 paper reads per question. Only `read_paper` consumes this allowance; profile sections and ordinary webpages read through `read_context` do not. Very long HTML is explicitly marked as truncated at 150,000 characters. Failed retrievals are reported as unavailable, not cited as successful reads. Answers include section buttons and original paper links. Article text and browser observations are untrusted evidence, never instructions.

`read_context` reads every directly listed public HTTP(S) page, including personal homepages, project sites, institutions, social profiles and coverage articles. The server generates stable IDs from Markdown links plus the rendered homepage anchors (including sidebar/header links). There is no person-specific allowlist. This directory and ranked link matches are included in the pre-refusal index search. Factual questions about a linked person or project are in scope even without mentioning Linxin; details absent from the local profile require a linked-page read. New rendered links automatically join the catalog locally; rebuild Jekyll and redeploy the Worker for production changes.

The tool accepts catalog IDs only, at most three webpages per call; these context reads do not consume the paper allowance. It follows up to four public HTTP redirects (including homepage domain changes), with a 20-second total timeout and a 2 MB decoded response limit. The model supplies short source-language search terms (including English equivalents for Chinese questions), so facts deeper in a page can be retrieved across languages. Scripts/styles are stripped; only an introduction plus question-relevant excerpts, at most 8,000 characters, enter model context. Up to 32 source texts are cached for 15 minutes, without visitor data or questions; reading does not require a separate summarization model call. Local fetches validate and pin public DNS addresses in the actual socket lookup; the Worker checks public DNS records before fetching each redirect target. Non-public hosts, IP literals, credentials, nonstandard ports and HTTPS downgrades are rejected. Outgoing links inside fetched pages are not recursively crawled. HTML/text pages are supported here; publication PDFs retain the existing `read_paper` path. Sites requiring login, JavaScript, or bot challenges may not be readable and are reported as unavailable.

Only successfully retrieved catalog entries can become external source citations. The browser displays those links only if their original URLs are in the page's anchors; clicking opens the source in a new tab. Automatic retrieval remains silent and never navigates the visitor's viewport. Source excerpts are untrusted evidence, not instructions. Site content can change and model factuality remains fallible.

Multi-turn context is carried in an authenticated, encrypted, origin- and browser-bound token, with up to **five recent conversation steps** (one user question plus one assistant answer per step; also bounded to 48 KB of UTF-8 text). Within a running turn, only the last five tool steps are retained, keeping each call/result pair intact and preserving the current question. Old tokens are trimmed when read, so the limit also applies to existing chats. Notes/excerpts for up to six papers and webpages combined are carried only while a retained exchange cites them. The fixed profile and system instructions are separate from conversation memory. The token expires after 24 hours. Session storage preserves the displayed transcript and token across page refreshes within the tab; older displayed messages are not sent back to the model. New chat clears context without resetting quota. Exact identity questions return a fixed personal-agent introduction without an LLM call; mixed questions still pass through the scope classifier. Model-based scope/factuality checks are not mathematical guarantees; tool and source allowlists are enforced in code.

Each in-progress turn expires after 15 minutes and permits at most eight tool steps. Step tokens are single-use, so replay cannot cause repeated paid calls. Request size, output size, provider timeout, per-client and overall request rates are bounded. The service does not log question bodies or secrets. Questions, recent conversation, profile facts, retrieved webpage excerpts and paper content are sent to OpenRouter and the selected model provider.

## Visitor messages by email

The **Leave me a message** suggestion sits next to **Experience** and starts a conversation. There is no separate message form or public send endpoint. The agent explains the maximum of **2 messages per visitor per UTC day** and asks for the message in chat. When a visitor explicitly supplies text to forward (including a follow-up after the agent asked for it), `send_message` sends it directly to the fixed owner inbox. Missing optional name/reply-to details stay empty. Complete send requests need no extra confirmation. The existing 20-question allowance applies to chat turns; sending a tool action does not consume an additional question credit.

The initial scope classifier separately identifies collect/send/retry intent from the visitor's own conversation. Only send intent enables the send tool; ordinary research turns cannot access it, even if a retrieved page asks for email. The backend also checks that message text and optional identity fields occur in user turns, and fixes the email subject, sender and recipient. It seals the authorized tool call to the visitor/origin. The browser only displays progress and submits that opaque state; it cannot replace the email body or report delivery success. In-progress sends may be replayed safely: the message ledger and Resend idempotency key determine whether to send or return the existing result. A receipt is chosen from actual backend results, in the current conversation language; it reports provider acceptance, not guaranteed inbox delivery.

Set `RESEND_API_KEY`, `MESSAGE_FROM` and `MESSAGE_TO` in the external local env file or backend deployment secrets. No API key enters Git, HTML or model prompts. The local configuration currently uses Resend's testing sender to the owner's Resend account email. The backend uses the [Send Email API](https://resend.com/docs/api-reference/emails/send-email) with plain text and a stable [idempotency key](https://resend.com/docs/dashboard/emails/idempotency-keys). Only visitor-provided message/contact fields are sent, not conversation history or IP/browser identifiers.

The daily limit is transactional in the existing persistent SQLite/Durable Object ledger and checks both IP and browser HMAC counters. Reducing the limit does not erase existing counts. Known provider rejection restores the reserved slot; ambiguous failures retain it because the provider may already have accepted the message. Retry/check requests reuse the exact sealed payload and request ID, including across midnight, rather than generating another email. The browser preserves an uncertain send token in tab session storage; this is encrypted and bound to that visitor. Tokens expire before the provider's 24-hour idempotency window. A previous uncertain delivery is resolved before another message is accepted. Ledger records contain hashes and state, not message bodies. The legacy `/api/messages` form endpoint returns 404.

## Daily visitor quota

Each admitted question consumes one of 20 daily credits, resetting at **00:00 UTC**. A shared persistent ledger also caps the entire site at **1,000 admitted questions per UTC day** across all IPs and edge locations. Tool calls and paper reads within that question do not consume additional credits. Identity answers, refusals, stopped turns and requests that fail after admission still count; invalid/forged requests rejected before admission do not. Duplicate initial request IDs and replayed tool steps are rejected before inference.

Quota is enforced transactionally in SQLite at `$HOME/.config/linxin-page-agent/quota.sqlite` locally (`AGENT_QUOTA_DB` can override the path), and in a SQLite-backed Durable Object in production. Restarts and new chats do not reset it. Separate counters are checked for the server-observed IP and persistent random browser IDs from local storage/cookies; every counter must be below 20. Only HMAC hashes are stored. Local requests use the TCP socket IP, ignoring forwarded headers; production uses Cloudflare's edge-supplied IP. Retain `VISITOR_HASH_SECRET` across deployments so counters remain associated with the same identities. Both health and agent routes apply burst limits before storage access; tool replay protection spans the midnight boundary.

Browsers cannot access MAC addresses. The combined policy resists a single cookie reset or a single IP change, but is not proof of a unique human: shared networks may share their 20-credit IP allowance, and simultaneously changing network and browser identity can evade anonymous recognition. No invasive device fingerprinting is used. Authentication would be needed for reliable per-person identity. Rate limits and the daily quota are not monetary caps; keep an upstream key spending limit for public deployment.

## Publishing with GitHub Pages + a Worker

GitHub Pages serves static assets and cannot hold runtime secrets. Deploy `_agent/worker.mjs` separately to Cloudflare Workers, or run the local adapter on a suitable Node host with equivalent environment-secret configuration. The backend is deployed at `https://linxin-page-agent.rm-social-song1.workers.dev`, with both `https://linxins97.github.io` and `https://linxins.net` allowed. Six backend secrets are configured. The GitHub Pages source now points to this endpoint; publish the frontend changes through the normal repository workflow.

1. In `_agent/wrangler.toml`, set the actual allowed production origins. Verify rate-limit namespace IDs do not collide with other Workers in your account.
2. In Cloudflare Workers **Settings → Variables and Secrets**, create `OPENROUTER_API_KEY`, `OPENROUTER_BASE_URL` and `VISITOR_HASH_SECRET` as **Secret**, not plaintext variables. Alternatively use Wrangler's secret prompts (do not put values in commands or source).
3. Build Jekyll first so `_site/index.html` contains the current header, sidebar and profile links. From `_agent`, deploy with `npx wrangler deploy` (`npx.cmd` in Windows PowerShell if script execution is restricted). This creates the `VISITOR_QUOTA` Durable Object using the included SQLite migration. The build regenerates the authoritative profile from `_includes/profile.md`; redeploy the backend when profile facts change. Missing quota storage fails closed.
4. Set the public `page_agent_endpoint` in `_config.yml` to the deployed **proxy origin** (for example `https://your-worker.workers.dev`). This is not the private upstream base URL. Rebuild GitHub Pages.
5. Verify a relevant question, a refusal, and a cited page jump on the deployed site.

GitHub Actions Secrets alone do not protect a value interpolated into public HTML/JS. Do not inject either upstream secret during the Jekyll build. If adding deployment CI, pass secrets only to the backend deployment service.

Security boundaries, residual risks, and pre-publish checks are documented in [SECURITY.md](SECURITY.md). No production API key is needed in GitHub Actions.

The model has two distinct reading tools: `read_context` for a profile section, catalog webpages, or both in one call, and `read_paper` for full publication contents. Tool schemas and prompts expose remaining paper/search budgets. Exhausted tools are removed, valid overlarge paper batches are capped to the available allowance, and a model that still requests an exhausted tool gets one final-answer recovery without another retrieval. The browser action protocol preserves compatibility with already open tabs. The eight-action-per-question bound remains.

Combined context reads validate both targets and obtain the section text from the authoritative server profile alongside fetched webpages. An empty target defaults to biography; it does not surface an internal either/or validation error.

Answer tool schemas list only currently verified citation IDs (read sections and successfully retrieved documents). Known IDs in the wrong citation array are reclassified, but unknown/unread citations are never silently removed. An invalid answer with available evidence receives at most one bounded model rewrite using those sources, without consuming another visitor question. If evidence is absent or the rewrite still fails validation, the candidate answer is withheld and a brief evidence-unavailable message is returned instead of an internal error.
